## 07. 기술 구현 정보

### 1) Frontend — 화면 구현 및 API 연동 (v1.0.0)

React 18과 TypeScript로 소비자가 농산물 가격을 쉽게 확인할 수 있는 화면을 만들었습니다.

- 메인: "오늘 살까, 기다릴까?" 검색과 저렴해진 · 비싸진 농산물 목록
- 가격 정보: 품목별 현재가, 전일 대비 등락, 7일 후 예상 가격 카드
- 가격 상세: 가격 추이 · 예측 그래프, 가격 변동 원인, 관심 등록 · 가격 알림
- 커뮤니티: 레시피 마당과 자유게시판
- API 모듈마다 mock 데이터를 두어 백엔드 연동 전에도 화면 개발과 시연이 가능하도록 구성

가격과 날짜처럼 숫자가 많은 데이터를 **그래프 + ▲▼ + 한 줄 설명**으로 단순하게 보여 주는 데 중점을 두었습니다.

### 2) Data — 데이터 수집 및 처리 파이프라인 (v2.0.0)

```mermaid
flowchart LR
    A["공공 API<br/>도매가 · 경매 · 기상"] --> B["Python 수집기"]
    B --> C["raw 번들<br/>일 · 월 단위 파일"]
    C --> D["Spark 정제<br/>silver"]
    D --> E["학습용 데이터<br/>gold Parquet"]
    E --> F["AI 예측 모델<br/>서비스 DB"]
    G(["Airflow<br/>일 단위 배치"]) -.-> B
    G -.-> D
```

| 데이터 | 출처 | 용도 |
|---|---|---|
| 도매가격 | aT · KAMIS 가격 API | 예측 대상 가격 |
| 경매 원천 (경락 물량 · 산지) | aT 경매 원천정보 API | 출하량 · 산지 특성 |
| 관측 기상 (ASOS) | 기상청 | 생산지 기온 · 강수 |
| 단기 · 중기예보 | 기상청 API허브 | 앞으로의 날씨 변수 |

- **수집:** 출처별 수집기가 응답을 값 그대로 저장
- **저장:** raw 원본은 읽기 전용으로 두고 덮어쓰지 않음
- **전처리:** 결측 · 중복 · 품목별 형식을 검토해 silver 데이터로 정제
- **병합:** 날짜 · 품목 · 지역 기준으로 서로 다른 출처를 맞춰 gold Parquet 생성
- **자동화:** Airflow로 매일 수집 · 전처리 작업 실행

### 3) 배치 처리 및 저장 구조

도매가는 평일마다 갱신되기 때문에 **일 단위 배치** 구조를 사용했습니다.

| 구성 | 내용 |
|---|---|
| Airflow | API 서버 · 스케줄러 · DAG 프로세서, LocalExecutor |
| Spark | Standalone 클러스터 (master 1, worker 2) |
| HDFS | NameNode 1, DataNode 2 |

- 수집기가 남긴 원본을 **하루 · 월 단위 파일 하나로 묶는 raw 번들** 적용
  - 도매가 · 경매 · ASOS: 응답 행을 한 줄씩 담은 `JSONL.gz`
  - 단기 · 중기예보: 원본 파일을 그대로 담은 `tar.xz`
- 묶을 때 값을 바꾸거나 행을 거르지 않고, 출처 정보와 제외한 행 수를 manifest에 기록
- 계층별 저장 경로 규칙: `raw` → `silver` → `gold/{table}/year=/month=/` → `quality/{table}/`

### 4) 데이터 확장 및 품질 관리

v2.0.0에서는 도매가 30일 예측을 위해 데이터의 기간과 종류를 넓혔습니다.

- 농산물 35개 품목 유지, 예측 범위를 D+1\~10 · 20 · 30으로 확장
- 경매 원천 · 단기예보 등 과거 데이터의 수집 기간을 2021년부터로 확대
- 주요 생산 지역 16곳의 관측 기상과 단기 · 중기예보 활용
- 같은 날짜가 일 단위 · 월 단위 파일에 함께 있으면 작업을 실패시켜 중복 반영 방지
- 테이블마다 기간별 품질 리포트(JSON)를 남겨 누락 · 범위를 확인
- 작업은 다시 실행해도 결과가 같도록(멱등) 만들고, 실패하면 0이 아닌 종료 코드를 반환

## 08. 트러블슈팅

### 1) HDFS 소형 파일 증가 문제

**문제**
API 응답을 호출 단위로 저장하면 작은 파일이 계속 늘어나 HDFS NameNode의 관리 부담이 커질 수 있었습니다.

**대응**
수집 원본을 하루 · 월 단위 파일 하나로 묶는 raw 번들 방식을 적용했습니다. 묶을 때 값은 그대로 두고, 무엇을 묶었는지 manifest에 남겨 원본 추적이 가능하도록 했습니다.

**배운 점**
HDFS에서는 데이터 용량뿐 아니라 **파일 수와 저장 단위**도 중요하며, 데이터 활용 목적에 맞게 배치 구조를 설계해야 한다는 점을 배웠습니다.

### 2) 기상청 API 일일 호출 한도로 과거 예보 수집 중단

**문제**
AI 학습에 필요한 과거 단기예보(발표일 1,096일분)를 수집하던 중, 기상청 API허브의 **일일 최대 호출 용량 제한**으로 수집이 멈췄습니다. 100일분을 받는 데에만 원본 약 15,000건, 5GB 이상이 필요했습니다.

**대응**
날짜 범위를 팀원별 담당 문자로 나눠 각자 본인 인증키로 수집하는 **팀 분산 수집 스크립트와 안내문**을 만들었습니다. 저장된 원본은 해시로 검증하고, 다시 실행하면 완료된 파일은 자동으로 건너뛰도록 했습니다. 같은 방식을 과거 경매 원천 데이터 수집에도 적용했습니다.

**배운 점**
외부 API를 쓸 때는 호출 구현뿐 아니라 **호출 한도 · 재시작 · 중복 방지**까지 고려해야 하고, 여러 사람이 실행하는 작업일수록 안내문과 검증 절차가 중요하다는 점을 배웠습니다.

### 3) 외부 데이터 수집 기간의 제약

**문제**
일부 경매 · 가격 · 기상 데이터는 API로 원하는 과거 기간을 받기 어렵거나 시간이 오래 걸렸습니다.

**대응**
데이터별 제공 범위와 수집 가능 기간을 확인하고, API로 받기 어려운 기간은 포털에서 받은 CSV를 파이프라인 원본 형식으로 바꾸는 변환 스크립트로 보완했습니다.

**배운 점**
공공데이터를 활용할 때는 실제 데이터의 **제공 기간, 누락 여부, 형식 차이**를 먼저 확인해야 한다는 점을 이해했습니다.

### 4) 서비스 대상 전환에 따른 데이터 재정의

**문제**
중간 피드백에서 "소매가는 변동 폭이 작아 소비자의 구매 결정에 영향이 적다"는 지적을 받아, 서비스 대상을 소비자에서 농업인 등 도매 관련자로 바꾸게 되었습니다.

**대응**
예측 대상을 소매가에서 도매가로 바꾸고, 예측 범위를 7일에서 30일로 늘리는 데 맞춰 수집 대상 · 기간 · 테이블 구성을 다시 정의했습니다. 가격 원본의 소매 행은 수집 범위에서 제외하고, 제외한 행 수는 기록으로 남겼습니다.

**배운 점**
서비스 방향이 바뀌면 화면보다 먼저 **데이터 정의**가 바뀌어야 하며, 데이터 범위를 문서로 합의해 두는 것이 팀 작업의 기준이 된다는 점을 배웠습니다.

## 09. 학습 내용 및 회고

### 학습한 내용

**Frontend (8\~9월, v1.0.0)**

- REST API 연동과 mock 데이터 기반 개발

- 소비자 관점의 쉬운 UI 구성

**Data (10\~11월, v2.0.0)**

- Python을 활용한 공공 API 데이터 수집
- Airflow 기반 일 단위 배치 작업 구성
- Spark를 활용한 데이터 정제 · 병합과 Parquet 생성
- HDFS의 저장 구조와 소형 파일 관리
- 호출 한도 · 재시작 · 중복 방지를 고려한 대량 수집
- 데이터 수집 주기, 정합성, 처리 효율 검토

### 회고

농담 프로젝트에서는 프론트엔드와 데이터 업무를 모두 맡으며 서비스의 데이터 흐름을 처음부터 끝까지 경험했습니다.

v1.0.0에서는 소비자가 농산물 가격을 쉽게 확인하도록 화면을 만드는 데 집중했고, v2.0.0에서는 도매가 30일 예측에 필요한 데이터를 수집하고 가공하는 역할을 맡았습니다.

특히 서비스 대상이 소비자에서 농업인으로 바뀌는 과정을 겪으며, **누구를 위한 서비스인지에 따라 필요한 데이터와 예측 범위가 달라진다**는 점을 배웠습니다. 또한 데이터의 수집 방식, 저장 구조, 전처리 과정이 서비스의 안정적인 운영에 직접 영향을 준다는 점을 체감했습니다.

화면에서 데이터를 쓰는 입장과 파이프라인에서 데이터를 준비하는 입장을 모두 경험하면서, 두 영역이 어떻게 맞물려야 하는지 이해할 수 있었습니다.
